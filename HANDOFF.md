### The two repairs that made the join possible

Diagnosis correction worth keeping: the repository-identity check was **not**
the only blocker, and re-running core at a matching commit was necessary but not
sufficient.

1. `_validate_trusted_join` compared whole `campaign.policy` documents.
   `catalog_profile` and `input_paths` differ by construction between profiles,
   so no core campaign could ever join a shared or overlap campaign, at any
   commit. The guard now compares the analysis-relevant subset; everything else
   stays strict and input identity is still enforced by digest.
2. Serializing the joined aggregate exceeded the 1,000,000-item default. The
   measured document is 1,013,696 items in 8,101,263 bytes, so
   `_PUBLICATION_JSON_LIMITS` binds 4,000,000 items at that one call site. This
   bounds output built from validated evidence; untrusted readers are unchanged.

Both are covered by tests, including a check that the exemption test fails
without the fix.

## Key lessons retained

- Byte limits and structural item limits are independent, and both sides
  matter: r5 hit an input item budget, the trusted join hit an output one.
- An over-strict equality check can be as wrong as a missing one. Comparing
  whole policy documents made a legitimate operation impossible while proving
  nothing that per-input digests did not already prove.
- Scheduling, not compute, dominated this campaign. 160 cells needed about 90
  minutes of node time but waited hours behind Jenkins on a shared node.
- A successful SLURM exit is necessary but insufficient: load the immutable
  attempt, verify manifest/job/node/partition bindings, and rehash artifacts.
- Regenerate into a temporary destination and byte-compare before trusting or
  reusing existing output.
